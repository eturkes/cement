## Detail

### C2 — what verification proves

The owner-selected abstraction is coherent: the key stays exact, while a sealed recognizer declares the raw-input equivalence class. Witnesses ensure that a declared layout has appeared; they do not prove that discarded values are irrelevant to the answer.

Passing-but-wrong trace using the shipped lab grammar:

1. Two raw lab slips have the same title/ordered labels/section; both have normal potassium.
2. The learning pass confirms the same value-dependent output `{"abnormal":false}` twice and writes the witnessed layout program.
3. V1 validates the program; V2 finds witnesses; V3 sees identical outputs; V4 is nonempty. Compile support = 2, reviewers = 1, span ≥ 0. Replay compares the same stored output; deleting Patient changes the structure. Function/promotion bindings remain valid.
4. A new raw slip changes `Potassium: 4.2` to `Potassium: 9.0`. The defined projection returns exactly the old key, so resolve returns false.

This is a contract-level counterexample, not a claim to have run the unimplemented IR/lifecycle. A source-derived parser sketch confirmed the key equality on the repository fixture. An operation returning an extraction *plan* may legitimately ignore that value; an operation returning an interpretation may not. The contract needs that distinction. A wrong shared locator is simpler still: no projection restriction proves that a confirmed plan is correct.

Recommendation does not add another human gate. Keep the switch. Publish the limited guarantee, and use independent operation-specific checks where stronger semantics are required. No sampled battery can establish arbitrary future semantic correctness from the same model's confirmations alone.

### C5 — required state machine + interleavings

Use three distinct identities: latest projection setting used for new builds; latest promoted receipt used by follow; pinned receipt used by pinned. A version owns its projection. Setting P2 never reinterprets P1's keys. The next successful set promotion replaces all P1 members atomically; if no qualifying P2 version exists, keep serving P1 or return the appropriate failure, never manufacture a mixed set.

Pin these transitions:

- P1 selected → set P2 → resolve/export still use P1; promote P2 → follow uses P2; pin P1 → remains P1.
- Change switch, revise operation, revoke evidence or add contrary evidence between prospective/read steps. An operation must observe one committed snapshot, not independently acquired switch/program/function snapshots. A writer after that snapshot may change the next call; the result remains a snapshot, not a lease.
- Change current projection after inspect but before promote; expected function identity/locked planning must reject or construct exactly the now-current prospective set.
- Per-artifact promotion cannot bypass projection uniformity: it must be rejected or leave the whole function unservable until a uniform set receipt is checkpointed, with no answer from a partial set.
- `set_projection` revalidates V1–V4 under the same write transaction that appends/retire rows; a prior `test_projection` result is only a preview.

### C7 / X2 — source observation is the recurrence unit

Repeated delivery of one source event must not create another proposal. Regenerated responses need explicit lineage, not inference from text equality. Multiple legitimate calls must remain distinct; repeated callbacks for the same call must not.

An atomic insert with a durable uniqueness rule is needed. A filter-local set or read-before-submit check loses on restart/concurrent callbacks. The existing library's non-idempotent `submit_proposal` is not a dedup mechanism. A commit-then-error recovery path must enumerate or return the existing capture, not blindly append.

Match native call/result IDs in the current completed assistant response. Verify the tool name, arguments, result status and operation, and retain the relevant user request and model-specific response identity. A whole final response can combine hit and miss outputs, multiple operations, prose and scripts; it is not automatically the candidate output of each missed operation. Storing the final reply remains useful audit evidence, but operation-specific candidate data is a separate field.

### C8 — schema details to decide before M3.6b

Required design decisions, not a prescribed oversized schema:

- Durable source-observation identity/uniqueness and per-call provenance (C7).
- Source observation → successive merged judgments/examples, with one support credit per original observation (X1). Existing `examples.proposal_id UNIQUE` + immutable confirmed output cannot represent that evolution as written. A supersession/review-generation relation is one solution; raw transcript rows stay immutable.
- Optional historical invalidation relation if retired versions can be disabled independently of original evidence (C3).
- Explicit switch state CHECK: pinned requires both fields present; off/follow requires both absent. Probe of the literal boolean biconditional accepted `(off, receipt, NULL)` and `(follow, NULL, hash)`; positive controls accepted `(pinned, receipt, hash)` and `(off, NULL, NULL)`. SQLite in-memory probe rc 0. S3 must cover every half-populated combination, not just both-populated off.
- Composite `(receipt_id,function_hash)` binding; scope/revision binding for switch pins and projection references; hash/canonical validation of stored projection JSON. New `projection_id` must be part of the integrity reconstruction, not a detached FK beside already-sealed fields. `src/cement_runtime/system.py:258-277` shows the current explicitly enumerated receipt hash fields that need a deliberate new format/binding decision.
- Decide internal v2→v3 function-ABI receipt behavior. `_reconstruct_function_receipt` rebuilds using the current builder (`src/cement_runtime/system.py:2117-2134`); a builder that always emits v3 cannot reconstruct old v2 receipt hashes. Either preserve the receipt ABI or explicitly reset unreleased ledgers at this boundary. External v2 bundle readability does not by itself solve historical receipt reconstruction. This is a compatibility decision, not a demand to migrate released v2 ledgers; §1 already rejects those.

### X3 / X4 — content identity and version inspection

### X5 — executable predicate corrections
