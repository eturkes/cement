# M3 Unit-Split Draft

## S1 DECISIONS

### D1 — track order

**Ruling: (b) → (c) → (a), strictly sequential.** M3.1 removes `authority()` first. M3.2-M3.6 then replace the request lifecycle. M3.7 relocates the concrete command runtime only after the final `CandidateRequest` and CLI seams exist. No two units own `system.py`, `models.py`, `__init__.py`, or `cli.py` concurrently.

The deciding evidence is overlap, not conceptual preference. Track (b) is schema-neutral and independently landable. It deletes 11 tests / 409 method-span lines and rewrites 18 tests / about 87 lines before track (c) reaches a 511-method closure and changes or deletes 780-1,130 test lines. Landing (b) first removes its callback-only double plans and avoids adding an authority gate to the new submission API merely to delete it later. Track (a) must wait: its retained protocol currently names `CandidateRequest.request_id`, which track (c) deletes, while its concrete CLI import and source flags disappear in track (c). Moving (a) first therefore pays a protocol rewrite twice and temporarily leaves the core CLI unable to turn a miss into a proposal.

Rejected: **(c) → (a)/(b)** from map-m3-3 fork 12. Sequential ownership is right, but carrying authorization through the new schema/API cut wastes the measured 496-line track-(b) test edit and creates a throwaway gate on submission. Rejected: **(a) first**, for the stale `CandidateRequest` and crippled-CLI costs above. Rejected: parallel tracks; all three touch at least one of the four shared surfaces.

### D2 — enforced read-only `resolve`

**Ruling: settle the contract now; no new spike.** `resolve` must use a reusable Store-owned enforced-read context built from four layers: (1) an existing-only `file:` URI opened with `mode=ro`, `uri=True`; (2) `PRAGMA query_only = ON`; (3) a write-denying authorizer covering row writes, DDL, write-capable PRAGMAs, virtual-table changes, `ATTACH`, and `DETACH`; and (4) one explicit deferred transaction that always rolls back and closes. The public resolve route must bypass create-if-absent initialization. A missing path must fail with no file created. `immutable=1` is forbidden for a live ledger.

The research probe already selects this stack. `query_only` rejected writes but the same connection disabled it. The authorizer rejected injected writes with `SQLITE_AUTH` but the same connection could replace or remove it. `mode=ro` still rejected main-ledger writes after both Python guards were disabled and refused a missing path with `SQLITE_CANTOPEN`; however, alone it allowed TEMP writes, `ATTACH`, and writes to the attached database. The layers therefore cover distinct holes. `BEGIN` supplies one snapshot only; it is not a write barrier.

Rejected: map-m3-3's authorizer-only reusable transaction, because callback replacement leaves an ordinary read-write VFS connection. Rejected: current `Store.transaction(write=False)`, because it commits and can upgrade. Rejected: `query_only` or dump comparison alone, because one is disableable and the other is observational. Rejected: `immutable=1`, because a concurrent writer made the immutable connection return stale data.

### D3 — coarse versus split schema/API cut

**Ruling: split the coarse cut into three green core checkpoints, with the CLI caller cut inserted before final deletion, despite the giant-file reread cost.** M3.3 adds proposal-owned immutable scope/input plus explicit submission on a dual-compatible schema v3. M3.4 moves every proposal/review/report/event consumer onto those direct bindings. M3.5 switches all core CLI callers to the final APIs. M3.6 then deletes `requests`, lease/retry/polling code, lifecycle models, and the compatibility column under schema v4.

The measured existing production surface already gives a 1,095-line lower bound before new submission code: `handle` 271, `_fail_generation` 32, `_outcome` 116, `request_status` 14, proposal read/project methods 129, `review` 231, pending-gap projection 42, plus about 90 schema lines, 70 model/export lines, and at least 100 lines of request-bound report/source integration. A direct record boundary plus a source-backed convenience wrapper and optimistic revision recheck add about 180 lines, placing the coarse cut at roughly **1,275 production lines**. Its measured test churn is another **780-1,130 lines**. That crosses map-m3-3 fork 13's approximately 1,200-production-line trigger.

The one-window rule independently forces the split. M2.u3b1 changed 765 production lines plus 4,421 test lines at `main=92%` and `impl=78%`; M2.u4b changed 776 production lines plus 3,725 test lines at `main=81%` and `impl=92%`. MAIN now pays both halves from one 240K window. The two additive checkpoints cap at about 280 production / 240 test lines; the final close deletes about 600 raw production / 320 test lines but authors fewer than 170 new or rewritten lines. Each stays below the analogous judgment surface while preserving one schema version per schema-changing green checkpoint. Re-reading `system.py`/`test_system.py` three times is cheaper than opening a unit already larger than past non-cofitting halves.

Rejected: one coarse v3 cut, because its implementation half alone is at least a past `impl=` peak. Rejected: a same-version transient schema, because two green checkpoints with incompatible fingerprints under one `user_version` make the version lie. Rejected: a request-like renamed table, because that preserves the lifecycle being removed. The split deliberately yields v3 then milestone-final v4; both reject earlier ledgers before mutation.

### D4 — assurance tiers and tags

**Ruling:** M3.1-M3.7 are `tier=kernel` and tagged `oracle`; they change public ABI, authorization posture, storage identity, concurrency rules, resolution validity, process containment, or packaging boundaries. M3.7 also carries `prod` because wheel/sdist membership is a validator-gated artifact. M3.8 is `tier=data`, tagged `prod`: the demo/transcript is revalidated by the normal suite and by live execution at use. M3.9 is `tier=docs`, tags `-`: it re-derives claims after all behavior is fixed. No data artifact pays the kernel oracle campaign, and no judgment-bearing code relies only on an artifact validator.

Rejected: treating the relocation as data merely because most bytes move unchanged; process containment, import direction, public exports, and failure normalization remain kernel contracts. Rejected: combining the demo and final claim pass; M2.u5a/u5b already proved that the data and docs tiers carry different failure modes and gauges.

### D5 — verification scope of `resolve`

**Ruling: evaluate the full current six-check `verify_function` snapshot, then call M2's `evaluate`; never project a second weaker function and never answer from a historical receipt.** The result contract must distinguish three states: failed current verification (`verification.passed is False`, no match evaluation), a verified ordinary miss (`FunctionMatch.matched is False`), and a verified hit. A failed verdict is not a plain miss and is not automatically `IntegrityError`; structural corruption may still raise `IntegrityError`. The public result should pair the existing `FunctionVerification` with `FunctionMatch | None`, so it exposes the ordered checks without duplicating their vocabulary.

This is the only alternative that makes README paragraph 1's “once built and verified” the runtime gate, reuses M2's one authoritative reconstruction, includes P6's current persisted checkpoint, and answers current ledger state. A narrower private projection would create a second validity contract with no independent oracle. Reconstructing the latest receipt would intentionally answer sealed historical state after current revocation or policy drift. The cost is release semantics, not an omitted optimization: M3.2 must record cold/warm time and peak RSS at 1, 1,000, and 50,000 entries, compare against direct `verify_function` + `evaluate`, and corrupt first/middle/last rows. No cache may land without an invalidation identity.

Rejected: narrow current-row projection, because it weakens or duplicates P1-P6. Rejected: reconstructed receipt, because it is historical. Rejected: treating every failed verification as `IntegrityError`, because ordinary supported suspension can make P6 false. Rejected: calling “pure” cheap; the acceptance record must publish the measured whole-set cost.

## S3 UNIT DETAIL

**Gate identity for every unit:** `uv run python -m unittest discover -s tests -t .`. This is the sole configured gate. A `prod` unit adds the named artifact validator; it does not replace the suite. An `oracle` unit adds: a contract attack before implementation, an independent reference implementation in an isolated worktree, a diff-blind contract-derived suite, an independent mutation catalogue, a pristine parallel control, per-mutant patch/liveness proof, byte-exact restore, and MAIN replay of every survivor. The unit-specific corpus below seeds that campaign.

### M3.1 — remove the authority callback

**Scope.** Hard-delete `AuthorityCheck`, `System(..., authority=...)`, callback validation/storage, `_authorize`, and all 11 production call sites. Preserve every actor/reviewer argument, validator, persisted field, receipt/hash input, event field, and projection. Collapse `verify_drafts` to one authoritative plan under its write transaction. Collapse `promote_function` to one locked plan; the caller's expected function hash remains the content gate, but member/candidate/retired transition-set identity is no longer a separate guarantee after the callback window disappears. Preserve the explicit empty-union rejection before clock, ID, or durable writes. Keep the schema and `SCHEMA_FINGERPRINT` byte-identical.

**Acceptance-contract seed.** `inspect.signature(System)` has no `authority`; passing it raises Python `TypeError`; the repo has zero `AuthorityCheck`, `_authority`, or `_authorize` references. Every former mutation succeeds without an in-runtime permission decision and records the supplied actor/reviewer exactly where it did before. `verify_drafts` calls `_draft_verification_plan` once. `promote_function` calls its plan once under `BEGIN IMMEDIATE`, rejects an empty union before clock/ID/write, and still rejects an incorrect expected hash. `SCHEMA_VERSION`, `SCHEMA`, and `SCHEMA_FINGERPRINT` are byte-identical to the parent commit.

**Probe corpus.** Drive all 11 production call sites, including all three review decisions, with distinct actor labels; read each label from its row/receipt/event. Mutate away one label write at a time. Delete the empty-union branch. Move clock/ID before it. Reintroduce an authorization-shaped preflight. Weaken the locked expected-hash comparison. Assert a write-denying external wrapper can still stop a call before Cement while the same unwrapped call proceeds. The reference implementation must independently choose and justify the one-plan transition semantics.

**Normative claims.** Rewrite map-m3-2 rows S3-002, S3-003, and S3-006-S3-016. Preserve and re-pin S3-001, S3-004, S3-005, and S3-017-S3-028. The removal must be described as loss of an internal defense-in-depth hook, not as actor removal or authenticated supervision.

**Risks.** A broad deletion can erase reviewer diversity or promoter provenance; callback-specific tests also carry unrelated read-only/tail/order checks; removing the whole set-promotion preflight can reopen the `cf274a4` empty-union hole; retaining ignored compatibility keywords creates a false security belief.

### M3.2 — full-verification read-only resolver

**Scope.** Add an existing-only Store construction mode and a reusable enforced-read context. Its connector uses an escaped `file:` URI with `mode=ro`, `uri=True`, `query_only`, the complete write/DDL/PRAGMA/attach authorizer, one `BEGIN`, unconditional rollback, and close. Factor `verify_function` so its six-check core can run on a supplied connection without nesting transactions; both public `verify_function` and `resolve` use the enforced context. Add `System.resolve` and a frozen `FunctionResolution` pairing `FunctionVerification` with `FunctionMatch | None`; evaluation occurs only when verification passes. No resolver path suspends, quarantines, emits, allocates IDs, calls the clock, invokes a source, or commits.

**Acceptance-contract seed.** A missing path through the public existing-only route fails and creates no file. A valid call opens exactly one `mode=ro` connection, observes `query_only == 1`, installs the deny authorizer before resolver SQL, stays `in_transaction` through the last helper, rolls back, and closes. Injected `INSERT`, `UPDATE`, `DELETE`, DDL, write PRAGMA, virtual-table DDL, `ATTACH`, and `DETACH` fail with `SQLITE_AUTH`; with the authorizer deliberately disabled and `query_only` turned off, a main-ledger write still fails with `SQLITE_READONLY`. Full dump and file digest remain equal. Failed verification yields `match=None`; a passing document yields the exact M2 `evaluate` hit/miss. Ordinary suspension/drift is a failed verdict, while malformed bound content still raises `IntegrityError`.

**Probe corpus.** Healthy empty, one-entry, 1,000-entry, and 50,000-entry functions; hit, near miss, canonical-equivalent input, no current receipt, suspended member, policy revision, and first/middle/last corruption for each six-check family. Mid-call commit/rollback injection; attached-database and TEMP writes; missing path; symlink/non-file/path-Unicode cases inherited from Store. Record cold/warm wall time and peak RSS against direct `verify_function` + `evaluate`; require no extra full-set pass and no cache. The reference implementation must use a different connection-helper structure but return byte-equal models.

**Normative claims.** Rewrite map-m3-3 rows S4-R01, S4-R02, S4-R04, S4-R14, S4-A01, and the resolver half of S4-A02. Keep S4-T01. Public prose must say “one current six-check snapshot,” distinguish an unverified function from a domain miss, and never equate pure with cheap.

**Risks.** URI escaping can open the wrong path; `mode=ro` alone permits TEMP/attached writes; an incomplete authorizer list leaves capability holes; nested `verify_function` transactions split the snapshot; returning the embedded document through CLI serialization can emit up to 64 MiB accidentally; a resolver-only path that still calls default Store initialization creates the missing ledger it claims to refuse.

### M3.3 — proposal-owned schema v3 and explicit submission

**Scope.** Introduce schema v3 as a green compatibility checkpoint. Add immutable `operation`, `operation_revision`, `input_json`, and `input_hash` to `proposals`; make legacy `request_id` nullable and retain its FK only for the still-present `handle` path. Every legacy insert also fills the new fields. Remove `CandidateRequest.request_id`. Add two final library seams: `submit_proposal(..., candidate, expected_operation_revision=...) -> ReviewRequired` records a caller-generated candidate, and `generate_proposal(...) -> ReviewRequired` snapshots the operation, invokes the configured `CandidateSource` outside every transaction, then delegates to the direct seam. `ReviewRequired` retains only `proposal_id` plus its submission-only tag. Every invocation is a fresh attempt; no content deduplication or caller key exists.

**Acceptance-contract seed.** Proposal direct fields are required, canonical, hash-bound, and operation-FK/scope consistent. The compatibility `request_id` is either null or points at the matching legacy request. Direct submission requires the caller's expected revision; generation captures the revision before calling the source; both re-read it under the proposal write lock and raise `StateError` with zero proposal/event rows when it changed. The source call observes no transaction. Missing/broken sources raise `CandidateSourceError` directly and persist no failure state. Two equal sequential or concurrent invocations create two distinct pending proposals. The return exposes only a proposal ID, never candidate output. Shared system evidence-building fixtures use the new seams; only lifecycle-specific tests continue through legacy `handle`. A real v2 ledger is rejected byte-identically; a fresh v3 ledger has the exact derived fingerprint.

**Probe corpus.** Same candidate twice, concurrent equal candidates, source exception, malformed output/provenance, source result mutation after return, source blocked while a writer commits, revision change during generation, wrong expected revision before direct submission, partition/operation `LIKE` colliders, large bounded input/output, and event sequence rollback. Mutate the second revision check, direct scope columns, each digest comparison, nullability/FK, no-lock boundary, and proposal-ID freshness. The reference implementation must implement the direct seam first and layer source generation without sharing MAIN's helper decomposition.

**Normative claims.** Rewrite map-m3-3 rows S4-R06, S4-R15, S4-A03, S4-A08, S4-A10, S4-P02, and S4-C07. The temporary coexistence with `handle` is an internal checkpoint only; no claim may describe request IDs as part of the new seam.

**Risks.** Nullable compatibility fields can become a permanent shadow lifecycle; SQLite `UNIQUE` semantics over nulls can hide an accidental dedupe rule; source exceptions can leak arbitrary text; candidate generation can regain a lock through helper reuse; direct submission without an expected revision admits knowingly stale output; exposing the proposed output in the acknowledgement violates the hidden-candidate guarantee.

**Normative claims.** Rewrite map-m3-3 rows S4-R01-S4-R03, S4-R07-S4-R13, S4-R15-S4-R22, and S4-C01-S4-C08. Refresh the operator-facing halves of S4-A01-S4-A03. Do not revive automatic-fallback wording merely because the optional runner still exists elsewhere.

**Risks.** As-dict serialization of `FunctionResolution` can print the whole document; exit 6 can change channel/media type; direct submission can expose candidate bytes in its acknowledgement; argparse abbreviation can make removed flags appear to survive; CLI construction can recreate a missing ledger before resolve; source-runner imports can survive in a helper even after parser removal.

## S5 POLISH DEFERRALS + OPEN QUESTIONS

These items are off the M3 MVP spine. MAIN should append them to `.agent/polish.md` only if they are not already represented; each row is born with its close check.

1. **Separately installable command-source distribution.** The source/sdist example is sufficient now. Acceptance: a second versioned wheel installs beside a wheel-only `cement-runtime`; core metadata has no provider/runtime dependency; importing core loads no optional module; the second wheel exposes one documented runner command; the root configured gate plus a clean two-wheel smoke pass; release/version ownership is explicit.

2. **Resolver cache or pooled read connection.** M3 deliberately pays full P1-P6 per call. Acceptance: cache identity binds database identity, current operation revision, latest receipt sequence/hash, and every state change that can fail a check; first/middle/last corruption never returns a cached hit; concurrent writer tests prove invalidation; 1/1,000/50,000 benchmarks show a material cold/warm improvement; the uncached oracle and cached result are byte-equal; no long-lived read transaction blocks writers.

3. **Explicit quarantine/repair command after a resolver failure.** Pure `resolve` only reports. Acceptance: a separately named mutator consumes a displayed failure identity, rechecks under one write lock, changes only still-affected artifacts, emits one bounded event, is idempotent on rerun, and leaves an ordinary domain miss untouched; a race that moves the state returns conflict with no write.

4. **Caller-lifecycle helper and outbox example.** Core owns no request lifecycle. Acceptance: an optional example durably binds a caller logical-operation ID to partition, operation revision, canonical input, candidate content, and source revision; same-ID/different-content fails; an at-least-once relay probe demonstrates duplicate Cement proposals after the acknowledgement crash window; docs call this lost-intent protection, never exactly-once submission.
