## A

The proposed detector is viable; `row-only/digest/bound` alone is insufficient to specify its adapters.

- **Exception provenance matters.** `system.py:413-420`: `_policy_from_text` lets malformed JSON raise `ValidationError`, but non-object JSON raises `IntegrityError("stored policy is not an object")`; malformed policy objects raise `IntegrityError("stored policy is invalid")`. `function_report` catches only `(TypeError, ValidationError)` at `:2654`; it propagates those two `IntegrityError` messages unchanged. Snapshot verification catches both at `:3025` and collects `operation policy is invalid: {exc}`. Project-current-build and promotion planning propagate. Preserve the original exception, not only `str(exc)` or a single invalid label.
- **Scalar order is not shared.** Report: revision bounds → JSON type → hash syntax → parse (`:2639-2653`). Snapshot: revision type → hash type → JSON type (`:3011-3019`). Promotion: revision type → JSON type → hash type (`:4753-4758`). Thus "type checks as (3)" in the plan misses an actual order difference. Keep the profiles explicit even where current SQLite types make a guard defensive.
- **Text/hash behavior differs.** `_project_current_build` checks only `canonicalize(...).digest` (`:1345`); report raises at the first noncanonical-text check (`:2656-2659`); snapshot collects noncanonical text and digest mismatch independently (`:3028-3033`); promotion short-circuits its OR (`:4764`). A detector may calculate pure values once, but a wrapper must retain each caller's accepted states, error precedence and failure multiplicity. Row-only callers need not acquire canonical-text/digest checks.
- **Site 5 uses artifact policy.** `_run_verification`, `:4510-4520`: `current_ok` is registered-row equality; `test("operation-current", None, current_ok, "operation revision + policy binding")` runs before parsing `str(row["policy_json"])`. Replacing this with normalization of `registered` changes missing/stale/corrupt-operation behavior and can suppress the recorded current-operation test. Keep the source record explicit.

Reachability: `store.py:31-33,37` declares `revision INTEGER NOT NULL CHECK (revision >= 1)`, policy JSON/hash `TEXT NOT NULL`, and `STRICT`. For ordinary schema-conforming SQLite reads, revision type/minimum/max and non-string policy checks cannot distinguish valid stored row types; numeric text converts on insertion. Non-hex hash, malformed/noncanonical JSON and invalid policy object remain storable. An in-memory database using the exact `SCHEMA` confirmed revision 0 and nonnumeric text reject, while `[]`, `{}` and a `G`×64 policy hash store. This is a schema probe, not a persisted-ledger CLI reproduction. Fabricated rows/schema rewrites in tests remain their own compatibility surface.
