- Sizing evidence, all recorded while teammates carried implementation. M1: implementing teammates 27-33% (66-78K/240K) on a ~27K baseline (tool schemas + CLAUDE.md re-cache every turn), MAIN 76-96%. M2: `impl=` 59-92% across u1-u4b (u1 at 67% over one implementation pass plus one fix pass; a full-read reviewer hit 77%, 185K/240K), MAIN's coordination-only `main=` 62-93%. Under the current authorship split MAIN pays both halves from one window, so those ranges add instead of alternating — size remaining units well under M2's, and treat a unit whose implementation half alone reads like a past `impl=` peak as needing a split before it opens. No recorded gauge predicts a single-author unit, so an authorship change invalidates the whole estimator: open the milestone's first unit as a CALIBRATION unit, record its actual `main=` at close, and resize every later unit against that one measurement. A pre-open size trigger must also be a STATIC source-span budget — a trigger reading the completed diff (byte equality, post-factoring line counts) is unmeasurable at the moment it has to fire.
- Sole-rejecter isolation ("every other check still passes") is unachievable where checks are logically entangled: a duplicate `input_hash` also breaks `build_function` (`function.py:223`), and raw ABI corruption also breaks `_artifact_from_row`. The binding standard is the mutation criterion — for every check, some committed test must fail when that check's logic alone is deleted. Satisfy it for entangled checks by asserting the complete ordered check vector plus the detail of the check under test; never report a derivative check as passing to manufacture isolation.
- Set-level gates need multi-entry negative probes. Single-entry corruption tests prove a check can reject *a* row, not that it quantifies over *all* rows: u2 left mutants alive that suppressed later-row ABI/report/receipt failures. Corrupt the middle AND the last of ≥3 entries, because the loop index is exactly what a mutant weakens — a `middle or last` reading satisfied by middle-only probes left every last-row mutant alive across 8 separate u3b2 checks (ordinal contiguity, membership function-hash/input/entry-seal binding, report child-set + passing enforcement, the four scope bindings). Likewise, corrupting two constants at once pins neither — split compound conditions into one probe each.
- A read-only claim needs structural proof: SQLite `BEGIN` is not query-only, so `Store.transaction(write=False)` can upgrade and commit. Row-count snapshots pass while an injected `UPDATE` runs; prove non-mutation with a full table/schema dump comparison or a SQLite authorizer denying writes.
- Teammates can report completed work they did not do. u2's implementer reported "no probe was omitted" while eight required probes were absent; verify by grepping the artifact for the specific symbols a probe must use (e.g. `build_function` in the test file), not by reading the claim.
- Durable decision records live in `.agent/decisions/` (tracked). `.scratch/` is gitignored, so it never travels: a pointer into it is already dead in every clone and on every other machine, surviving only on the workstation that ran the wave — unreadable to exactly the reader it was written for. Seven decision records still open with `Inputs:` lines citing `.scratch/` paths that read as live references (rescue tracked in `.agent/polish.md`, while most sources still exist here). Anything a later unit must read — binding ABI field lists, cross-unit interfaces, the substance behind a cited input, any validator backing a durable claim — gets copied into tracked state at the time it is written, never cited across the boundary.
- A tracked file must never assert the ABSENCE of gitignored or machine-local state. `.scratch/ no longer exists` was written into memory, roadmap and the polish register from one workstation's view and was false on the other, which retired two recoverable artifacts (the u4b catalogue, the replay driver) by declaration and would have funded a rebuild of code sitting on disk. Absence is unobservable from a clone, so write the property that travels - gitignored ⇒ no clone reruns it - and confine machine-local existence to a named, expiring rescue window. Same discipline as the pointer rule: what the tracked file says has to be true for every reader of it.
- Two machines running the same reconciliation produce a duplicate, not a conflict. Local `bfc0a42` and upstream `14255dd` independently adopted one ops refresh, so the diverged branches shared no real disagreement and the resolution was `reset --hard origin/main` plus a re-apply of the few unique deltas - never a merge, which would have doubled every rewritten bullet. Diagnose by blob-comparing the shared files first (`git rev-parse <a>:<path>` vs `<b>:<path>`); identical blobs across most of the diverged set means duplicate work, and the side with dependent commits on top is the one to keep.
- Authorization written as a loop over members has an empty-set hole: an empty prospective union performs zero authority calls and still writes durable state. Gate collection emptiness explicitly before clock/ID/write work; never infer authorization from a loop that may not execute.
- Fixture values hide checks whose behavior only diverges past a boundary. Integers below 10 make base-10 and hex framing identical (5 encoding mutants survived); member/candidate ID sets that are equal make event cross-wiring undetectable; insertion order matching query order hides `ORDER BY` removal. Vary every fixture across the boundary its check depends on, and drive at least one integer to >=10.
- Enumeration completeness needs a tail sentinel beyond any plausible `LIMIT`. `LIMIT 1000` on both the retained and candidate queries left all 208 tests green, because the largest committed set was 101 rows against a 50,000-entry contract.
- Two reviewers with genuinely different lenses find disjoint defects. On u3b1, the correctness reviewer audited a deleted check and correctly cleared the deletion; the mutation reviewer independently proved the *surviving* half of that same check was killed by no test. Neither lens alone reaches both conclusions.
- A deliberate KISS baseline is the cheapest way to test a roadmap prescription. u3b's blob spike was dispatched to challenge the prescribed membership table and self-rejected on its own measurements (67 MB single row, 29.3 s parse, 1.9 GiB RSS, unindexable membership scan), which also transferred to the full-payload alternative and decided the fork on evidence rather than preference. u4's compose spike repeated the shape, proving compile-blocked state is persisted nowhere, that public `compile()` is a write, and that two ledgers differing only in a challenge-origin example's hidden `receipt_json` return byte-identical projections across all 13 existing read methods while the compiler diverges healthy-vs-`IntegrityError`. Dispatch the baseline whenever a roadmap line prescribes new structure or API surface.
- Function identity = verified-content identity, not activation identity. `cement-function-v2` entries carry `entry_seal` (`cement-function-entry-seal-v1` = the `cement-promotion-v2` field list minus `promoted_by`/`promoted_at_us`), recomputed on demand, so a prospective function hash is computable before promotion and re-promoting identical content yields one hash. Activation provenance stays in the unchanged ledger receipt; never move promoter/time out of `cement-promotion-v2`, because `_validate_promoted` recomputes from those row fields and that is the only detection of active-row provenance forgery.
- Draft eligibility is reconstruction, not status filtering: an eligible row matches current revision, `draft`, exact canonical input, AND the `build_hash` that `_project_current_build` independently projects, with `compile` and the batch enumerator sharing that one helper. Retiring superseded drafts at compile time does not work - a stale verified row demoted back to `draft` re-poisons the batch - and selection-side additionally lets revocation requalify an older correct build with no recompilation.
- An author-run mutation sweep certifies only the families the author already had in mind. u3a's implementer ran 39 isolated mutants and reported zero survivors honestly; an independent sweep of 76 then found 25 survivors, all in unenumerated families (digest framing/order/exclusions, non-draft status widening, ordering removal, last-row aggregate weakening, unexercised fault-injection gates). Always give the mutation sweep to a separate teammate with its own catalogue, and treat the implementer's sweep as a floor.
- Reviewer findings need MAIN's own probe before a fix dispatch: u3a's review named a surviving seal-domain mutant that was in fact killed by two existing ABI string pins, while the real gap was field order and length framing. The finding's substance held; its stated reproduction did not.
- Mutation harnesses must defeat `__pycache__` or they manufacture false survivors. CPython invalidates bytecode on `(mtime, size)`, so a mutation preserving a line's byte length (`2 *` -> `4 *`) applied within one mtime-second runs the ORIGINAL code and reports a live mutant as surviving. Purge `__pycache__` + set `PYTHONDONTWRITEBYTECODE=1` before every run, and prove the mutant reached the interpreter by importing the module and printing the value. Diagnostic tell: survivors correlating exactly with length-preserving edits. This cost u3b1 a needless fix cycle - MAIN reported both manifest-cap ratio pins as unpinned and a code reading agreed the ratio was runtime-derived, yet the original tests already killed the mutant through the rejection branch, where the scaled cap rises past the fixture. A survivor claim needs the mutant proven live before it becomes a finding.
- Target mutants by line number plus an asserted anchor string, never by occurrence index. u3b1's review sidecar numbered occurrences within its own replacement helper rather than globally, so the first replay mutated unrelated earlier definitions and reported false survivors; MAIN hit the same class of error from a stale line index. An anchor assertion on the addressed line fails loudly instead of silently mutating the wrong code.
- Drive MAIN's own mutant replay from the reviewer's catalogue `.jsonl`, never from the fixer's account: apply by anchor string, prove liveness, then let the full suite decide. A survivor list landing entirely inside the reviewer's proved-equivalent IDs is the closure signal. Driver `.scratch/main-replay/replay.py` and u4b's catalogue `.scratch/agents/rev2b-m2u4b-mutants.jsonl` are gitignored, so no clone reruns the claims they back, though both survive on the workstation that ran the wave — the tracked port is a copy-and-harden there, a rebuild anywhere else. Spec: N isolated clones of `src`/`tests`/`examples`, `PYTHONDONTWRITEBYTECODE=1`, per-mutant proof that the interpreter loaded the mutated module from the clone, byte-exact restore, `--reanchor` over a `difflib` line map, `--control` pristine sweep at full worker count. 61 mutants at 8 workers = ~13 min; 254 = ~50 min. Port to a committed dev tool is tracked in `.agent/polish.md` — a campaign run from scratch cannot back a durable claim, since the claim outlives the driver.
- Re-anchoring after a production fix needs a line MAP, not nearest-line guessing. u4b's `old` fragments (`partition = _name(partition, "partition")`, `WHERE partition = ? AND operation = ?`) occur 2-29 times in one file, so 8 of 61 mutants were unresolvable by proximity. Keep a byte-exact copy of the pre-fix target file (a reviewer's worktree serves) and map recorded line -> current line with `difflib.SequenceMatcher(...).get_opcodes()` over the two versions, then require a unique occurrence inside the mapped window. Three outcomes, all distinct: killed, survived, and superseded - `old` absent entirely means the fix deleted that code, which closes the finding legitimately.
- Run a pristine CONTROL sweep before trusting any parallel mutation run: the same suite in every clone at full worker count. Load-sensitive tests (`tests/test_source.py` drives real subprocesses and timeouts) would otherwise turn contention into phantom kills, and a phantom kill silently retires a real finding.
- Every mutant needs a positive control proving the PATCH applied, separately from proving the mutated module loaded. A u4c1 battery reported 7 false `SURVIVED` lines from two causes that both print exactly like a live mutant surviving: the patch step invoked bare `python`, absent from PATH, so it exited 127 without editing anything (use `uv run python`), and one mutant removed a parser block and reinserted it in the same slot, an identity transform. Assert `text != before` inside the patch, then assert the observable actually moved (re-import the module and check the rendered surface). Applies to reviewer catalogues too: an unconfirmed patch inflates the survivor list with rows no assertion can ever close.
- A diff-blind test author is worth its own dispatch: given the contract and normative docs alone, never the diff, u4c1's `test` teammate wrote 30 tests that failed 29 at baseline and passed 30/30 against MAIN's independent implementation, and three of its probes covered behavior MAIN's own suite missed (operation-name exactness against `=`->`LIKE`, runner decode totality, limit-above-count projecting the count). Contract-derived and implementation-derived suites converge on the same behavior only where the contract is genuinely unambiguous, so the divergences are the contract's real defect list. Full convergence is the maturity signal and the stopping rule: u4c5a's contract carried a measured probe corpus plus every exact string, and its diff-blind suite went 36 failures + 2 errors at baseline to 28/28 green against MAIN's implementation with zero divergences — no code defect, no contract defect, no coverage MAIN's own 21 tests lacked. Where the contract already names the strings and the corpus, budget the `test` dispatch as redundancy insurance rather than discovery, and spend the freed capacity on the contract attack, which is where u4c5a's only real defect came from.
- MAIN's u4c1 seam battery (9 mutants over `_Outcome`, `main`'s channel branch, the parser slot and limit forwarding; 9/9 killed) lived in `.scratch/mutants.sh` and died with the wave. Regeneration path: `cp` the target file, apply each mutant with an in-script `uv run python` `str.replace` asserting `text != before`, run ONE named test per mutant, restore from the copy, and finish with a `cmp` against a pristine copy plus a full-suite rerun. Port to a committed dev tool is tracked in `.agent/polish.md`; until then no durable claim may rest on it alone.
- `function_report`'s six detail lists do not share an ordering guarantee. Members project by `ordinal` and artifacts by `sequence DESC`, both canonical, but `pending_proposals` orders by `p.id` and `stale_revision_anomalies` by artifact `id` — random `prop_*`/`art_*` hex — so a truncated page of either is arbitrary though stable per ledger. A test asserting insertion order there passes twice and fails on the third run. Pin set membership plus per-ledger byte stability, or the projected page as a prefix of the same ledger's unbounded page.
- `stale_revision_anomalies` cannot be produced by any supported command: `operation revise` (`system.py:509`) retires every artifact it strands, and re-registering an existing operation is rejected with exit 4. Reaching the family for a test means bumping `operations.revision` with a direct `UPDATE`, which is faithful — the family reports ledger corruption — but means no test covers a production transition into it.
- Scope each fix batch by measurement, not prediction. u4b's correctness-lens fixes closed 10 of the mutation reviewer's 59 findings as a side effect; replaying the catalogue between batches scoped batch 2 to the 49 that actually survived, and the batch-2 brief became a precise per-mutant work list (`old`/`new`/current line/acceptance check) generated from the catalogue itself.
- A reviewer that finishes phase 1 near its window closes cleanly as a fresh successor seeded from its on-disk catalogue + harness + report, not as a revive. u3b2's `rev2-` -> `rev2b-` handoff cost nothing and the successor found 23 further gaps.
- Reusing one expensive fixture across several pins keeps the suite fast but couples them: u3b2's single 1,001-member tail sentinel carries four distinct enumeration guarantees, so weakening that one test unpins all four. Record the coupling wherever it is taken.
- A teammate declining the report `.md` write relays the full report through the `SendMessage` TOOL CALL, not assistant text, whether or not it announces the fallback: its transcript text blocks stay under ~450 bytes while the real 10-21 KB report sits in a `tool_use` input, so the global protocol's transcript-text extraction silently yields a stub. Harvest by dumping those inputs to the report path yourself (`jq`/Python over `.message.content[] | select(.type=="tool_use" and .name=="SendMessage") | .input.message`, longest-first), which is what makes an otherwise-invisible report addressable. Re-requesting the write does not help - u4a's reviewer refused twice, citing the same harness rule.
- SQL `=` can weaken to `LIKE` undetected whenever isolation fixtures use only hyphens: `_` is legal in partition/operation names AND is a `LIKE` single-char wildcard, and ASCII case folds by default. u4a had four independently live `=`->`LIKE` mutants pass all 307 tests. Scope-isolation fixtures need collision pairs (`tenant_a` vs `tenantXa`, `echo_1` vs `echoX1`) plus case variants, and for a revision lookup the collider must carry a DIFFERENT current revision so a wrong resolution is visible.
- Read-only proof and single-snapshot lifetime are separate guarantees needing separate pins. u4a's read-only test was already strong (write=False call cardinality, write-denying authorizer, full `iterdump()`, authority/clock mocks) yet a mid-method `connection.commit()` survived all 307 tests: the two reads then span two snapshots while every read-only assertion still holds. Pin it by wrapping the inner helper and asserting `connection.in_transaction` is still True when it runs.
- Behavioral tests cannot see resource contracts. Slicing after the fetch makes `LIMIT ?` bound to `limit + 2`, or an unbounded `LIMIT -1`, return byte-identical results - so an unbounded history scan hides behind a small caller limit. Pin exact materialization with a test-only connection/cursor proxy asserting the final bind and the row count actually fetched; this needs no production change, which matters when the storage module must stay byte-identical.
- A reviewer's proved-equivalent set can legitimately be EMPTY. u4a's mutation reviewer distinguished all 12 survivors with focused probes and mapped every one to a finding; treat a nonempty equivalence set as a claim to audit, not a default.
- Frozen public shape (keyword-only markers, dataclass field sets, return annotations, required-vs-defaulted fields) is invisible to behavioral tests: removing a `*`, adding a defaulted field, and changing return annotations all passed u4a's full suite. Pin with one `inspect.signature` + `typing.get_type_hints` test per frozen ABI, and record that it carries every shape pin at once.
- A validator whose RESULT is discarded is not a check. u4b's `_function_report_member` called `_request_id(row["membership_report_id"])` and `_digest(row["membership_entry_seal"])` purely for grammar and threw both values away, so a member row could be presented as valid while its report/seal binding was corrupt - and both the implementer's own sweep and its report claimed the rows were validated. Grep new validation code for calls in statement position: a validator's return value must be compared, bound, or recomputed against something, or the call only proves the field is well-formed text.
- Persisted-scalar conversion raises `TypeError` and `OverflowError`, not just `ValueError`. `int(None)` on a `NULL` column escaped u4b's `except (ValidationError, ValueError)` as a raw `TypeError`, the same class of leak u4a paid for with an unguarded `int(registered["revision"])`. Every path converting a stored scalar translates `TypeError`/`ValueError`/`OverflowError` to `IntegrityError`, or validates the exact stored type first (`_stored_int` uses `type(value) is not int`, which also rejects `bool`). Establish the schema's enforcement before rating an unguarded site, because the storage layer retires whole guard-defect classes: all 13 user tables are `STRICT` (`sqlite_sequence` alone excepted) ⇒ non-numeric `TEXT` unstorable in an `INTEGER` column, numeric `TEXT` converted at write, and integer columns `NOT NULL` ⇒ `NULL` unstorable. Exactly 3 nullable `INTEGER` columns exist repo-wide — `requests.lease_until_us` `store.py:56`, `proposals.reviewed_at_us` `store.py:97`, `artifacts.promoted_at_us` `store.py:163` — and every conversion reading one is already guarded (`or 0` `system.py:621`, `or now_us` `system.py:993`, `is not None` `system.py:1211` + `system.py:5159`), so guarded/unguarded tracks nullable/NOT NULL exactly; a fresh `System`, which every CLI invocation constructs, rejects a rewritten schema at construction ⇒ exit 5. A stored-scalar probe reaching a raw `TypeError`/`ValueError` therefore needs a schema rewrite, a fabricated row or a cursor proxy: label such probes fabricated and never cite one as a real-ledger repro. Keep the guards for defense in depth, not for reachability.
- Mutation probing is the high-yield review lens here: u1's first suite looked complete (14 tests, every field tamper covered) yet 15 of 52 mutants survived, because the whole-document hash check masks per-field validation — deleting the entry input-digest comparison kept all 95 tests green. A tamper test only pins its field when the outer `function_hash` is recomputed over the tampered content, so the field-level check is the sole possible rejecter. Apply the same construction to u2-u4 set-level gates.
- Root CLI `verify` reports failure with exit 0. `System.verify` returns a `VerificationReport` and raises nothing when verification fails (`system.py:3696-3721`); `cli.py:265-266` returns it and `main` unconditionally emits then returns 0 (`cli.py:339-360`). A scripted operator therefore cannot distinguish a verified artifact from a failed one by exit status. That is frozen precedent, not a model to copy — M2 u4c's `function verify` deliberately diverges to exit 6 with the payload still on stdout, the `diff`/`git diff --exit-code` convention. Any new command reporting a verdict makes this choice explicitly and pins both branches.
- No `cement_runtime` submodule import is store-free: importing any submodule first executes the package `__init__`, which imports `.system` → `.store` → `sqlite3`, even though `function.py` itself imports only stdlib plus `.errors`/`.json_value`. Ledger-freedom claims mean no `System` instance, no database path, no connection — never import-freedom. Prove one by patching `System` to raise on construction plus `sqlite3.connect`, never by inspecting the import graph; `tests/test_cli.py`'s in-process patch is the real pin. Three distinct properties need three distinct words, and a doc collapsing them misleads least-authority and sandbox design: `function eval` is ledger-free, not capability-free, since it opens and reads a filesystem path, so only its evaluation core is inert, and import-freedom is weaker still. A subprocess proves less than it looks — `function eval` dispatches ahead of the `--db`/`--partition` gate, so a child launched without `CEMENT_DB`/`CEMENT_PARTITION` rules out configuration alone while a leaf opening a database directly still answers 0 or 6. Process-level proof needs a syscall trace or a `sys.addaudithook` open/connect hook, with the `python -S` gap stated wherever the claim is made.
- A teammate's stated validator RESULT can contradict its own artifact. u4c's API mapper reported `ANCHORS-BAD: 0`/`UNKNOWN-CELLS: 0` while two entire tables sat unfilled, because it ran the validator before its final append and then reported the stale number. Briefs must order the validator LAST and forbid reporting done before it, and the lead re-runs the validator against the artifact instead of reading the number out of the report. This is cheaper and more reliable than the grep-for-required-symbols check, and it catches the honest-but-stale case that a completeness claim alone does not.
- Split granularity follows the size of the files the unit OWNS, not the size of the work. Where a unit owns giant files (`system.py`, `test_system.py`), each extra cut pays a full re-read and coarse slices win; where it owns small ones (`cli.py` 360 lines, `test_cli.py` 121), a fine cut costs a few thousand tokens and is strictly safer, because the chain rule lets one session close two sub-units while an overrun costs a whole session plus a half-finished tree. Undershooting is cheap, overrunning is not.
- A contract MAIN wrote is itself a review target, and its highest-yield defect is the BICONDITIONAL asserted where code implements one-way implication. u4c2's Decision 9.2 claimed `len(receipts) < limit` iff terminal page; the library fetches `limit + 1` and sets the cursor only when the extra row exists, so an exactly-`limit` page with nothing behind it is full AND terminal. Six of six accepted u4c2 findings were claim-vs-code gaps in MAIN's own contract, zero were code defects — dispatch the correctness reviewer against the CONTRACT before implementation, not only against landed code. Four consecutive sub-units (u4c2 6/6, u4c3, u4c4 9/9, u4c5a 6/7) returned findings that were overwhelmingly claim defects, so the pre-implementation contract attack is the default dispatch on a CLI leaf, and its recurring shapes are the biconditional, the unconditional claim that holds only under a fixture (u4c4's 499 B/entry against a 533 B displacing candidate; u4c5a's 304-byte empty document, which moves with the partition/operation/policy names it embeds), a stale structural inventory (raise counts, group counts), and a hazard declared injection-only that is in fact real concurrency behavior of the default-constructed `System`.
- One argument, two branches, one validator ⇒ divergent grading. u4c5a's contract attack broke the zero-code-defect streak on a shape worth naming: `function export OPERATION [--receipt-id ID]` passed the positional to `verify_function` on the live branch and to NO library call on the historical one, so grammar was graded by the library on one path and by receipt membership on the other, and an unset `$OP` reported not_found (3) where the sibling `function show` reports invalid (2). Whenever one leaf routes the same argument to two different library calls, check that EVERY branch grades it — import the library's own validator (`_name`, `_request_id`) and call it before dispatch rather than relying on whichever call happens to validate. The reviewer found it because it walked the two branches as a PAIR against the shipped sibling command, which is the probe to write into the brief.
- Exit class = the shared vocabulary; CHANNEL = the leaf's own stdout contract. `verify`/`verify-drafts` put a negative verdict on stdout because their stdout is a JSON channel; a byte-producing leaf must not, and measurement decides it — under a stdout verdict, `function export OP > f` at exit 6 leaves `f` holding 1,078 B of verdict JSON, because the redirect creates and truncates the target before the process runs. The opposite reflex fails too: one raised class for every negative is untruthful, since `artifact suspend` alone drives a checkpointed set to `passed=False` (vector `[T,T,T,T,T,F]`), so `integrity` misnames ordinary drift and the aggregate-limit vector misnames a capacity bound. Resolution shape: no bytes, empty stdout, the ordered check vector on stderr as the standard two-key error object plus one additive key, and a new `error` token so the token↔exit bijection survives.
- Two spikes self-rejecting on DISJOINT defects ⇒ the ruling is the SYNTHESIS, not either token. u4c3/u4c4 ruled from the asymmetry between two self-rejections on one axis; u4c5's each named a defect the other alternative did not have, and each independently recommended the other's core, so the correct disposition was a third one neither was assigned. Both self-rejecting is a usable verdict, never a stalemate, and three relations decide it. Both spikes naming the SAME dominant hazard ⇒ the council rule accepts it outright. Defects on one axis ⇒ prefer the alternative whose defect is CONDITIONAL on a regime the loser cannot improve — u4c3's PLAIN defect was unconditional and sat on the contract (every caller reimplements the gate) against STRICT's conditional, pre-existing one, and u4c4 repeated it with BOUNDED unconditional against FULL biting only at maximum cardinality where the alternative offers no relief. Each self-rejection describing a defect the sibling lacks ⇒ compose instead of choosing — and check the composition stays inside the frozen seam, which is what makes it cheap (here: a private `_Unverified` plus one appended `except` branch in `main`, leaving `_Outcome`, `_emit` and every existing mapping byte-identical).
- Wave-1 harvest is a first-class window cost, not overhead: one 268-anchor fact map plus two full spike reports consumed ~50K of MAIN before any contract line was written. At u4c-scale sub-units MAIN can afford wave 1 + fork arbitration + records in one window, with implementation landing in the next — so a unit whose fork needs spikes is effectively one window smaller than its line estimate suggests, and the size recheck belongs AFTER arbitration, when the surface is known.
- Pin every bound as an adjacent accept/reject PAIR (`max` accepted beside `max + 1` rejected). Corollary: a unit's own test repairs are a first-class cost - one signature change to a private method broke three zero-argument test doubles, and one new denial broke four more tests, none of which any span estimate sees.
- Skeleton-first is what makes a deliverable survive, and it must cover CODE deliverables, not only tables and reports. In one wave every deliverable whose brief mandated a seeded on-disk skeleton landed (a verdict table, a review report, an oracle branch), and every deliverable without one died unflushed in context - a diff-blind red suite whose worktree was still CLEAN after two explicit commit directives, while its author sat at 44% and had been working for a full window. A brief demanding a code artifact must require an immediate commit of a stub file naming every intended unit with a failing body, then one commit per filled unit; a marker plus a validator command is not a flush mandate. Corollary at close: a teammate's uncommitted worktree content is CONTENT - commit it on its own `wt/` branch rather than discarding it, because `TaskStop` cuts mid-tool-call and the agent's own final commit may have been issued but never executed.
- A diff-blind battery reaches defects a measured probe corpus cannot, because every probe error came from real SQLite while the code's guard has to be total. M3.2a's 32/32 corpus was green and its 48-test contract-derived battery still found `_transaction_error` reading `exc.sqlite_errorcode` unguarded: a `sqlite3.DatabaseError` constructed in Python escapes as `AttributeError` instead of the contracted mapping. The independent oracle had written `getattr(exc, "sqlite_errorcode", None)` for the same seam, so the differential named the fix before the battery named the bug. Keep both instruments — the corpus proves the mechanisms, the battery proves the contract, the oracle proves the coding.
- Closure for a hardening is a mutation sweep, not a green suite, and it is cheap enough for MAIN to run inline: 19 mutants over one file's enforcement predicates, verdict = the unit's own battery module rather than the full suite, ~2 minutes. That sweep is what proved two same-value-redundant setup operations (`PRAGMA busy_timeout` beside `timeout=10.0`, `setconfig(TRUSTED_SCHEMA)` beside `PRAGMA trusted_schema = OFF`) are killed only by a call spy, and it found the one allowlist member no test forced. Address every mutant by unique anchor with a `count == 1` assertion, prove the patch changed bytes, purge `__pycache__` under `PYTHONDONTWRITEBYTECODE=1`, restore byte-exactly, and run a pristine control first.
- A grant and an enforcement mechanism need opposite dispositions under the mutation criterion. An unforced ENFORCEMENT line (`PRAGMA query_only`) gets deleted: nothing can pin it. An unforced GRANT splits by reachability — `SQLITE_RECURSIVE` enables a genuine read, so a recursive-CTE probe forces it trivially and it stays; `SQLITE_SAVEPOINT` was reachable from no read path at all (both savepoint users are `write=True` sites), so it goes and its denial becomes the pin. Ask what probe could force it before asking whether it is harmless.
- Layer a capability claim by what the caller can reverse. A yielded raw `sqlite3.Connection` lets any caller run `set_authorizer(None)`, so an "enforced read-only connection" claim is false — but `mode=ro` is an open-time flag no method reverses, so the LEDGER stays read-only even after sabotage, measured by sha256. Write the layered claim (ledger protected unconditionally; TEMP and ATTACH protected only while the caller cooperates) and pin the limit with a test that asserts the escape works, so a future wider claim fails. A reviewer proving "the guarantee is impossible" may have proved it only for the outer layer.
- `git merge --squash` is the wrong harvest tool for a worktree deliberately based at a PRE-implementation SHA: `git diff main..wt/<name>` renders main's later commits as deletions, and the squash would revert them. Harvest the added file directly (`git checkout wt/<name> -- <path>`) and let the branch keep its baseline-red credential.
- Skeleton-first now has its control. In one wave the deliverable given a stub-commit mandate (every intended test NAME committed first with a failing body, then one commit per filled test) landed 52 commits / 48 tests / 22 of 22 obligations at 65% of its window, while the deliverable given the same mandate in PROSE — with no stub artifact to seed — produced nothing across three polls and one flush directive. The mandate has to name an artifact the agent can create in its first tool call; a description of flushing is not a flush.
